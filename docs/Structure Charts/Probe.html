Probe.java structure charts

A structure chart, from Yourdon and Constantine’s Structured Design, shows which modules call which, and what passes between them on each call. It leaves out the order of statements inside a module. Probe.java has 18 modules. The reporting copy, a copy of a student’s compiled class with a call to Probe added at each step, calls its public methods, and no class in src/main builds that copy yet. Each of the six charts therefore starts at an entry point of the class instead of at a caller.

Reading the charts

In Structured Design a module is a named piece of code that a caller can invoke and get control back from. In Java that is a method or a constructor. Each symbol below comes with the line in Probe.java that produces it.

Module

One method or constructor in Probe.java. The chart shows what it does for its caller, not the statements inside it.

Data couple

A value passed on a call. The hollow circle marks the tail, and the arrow points the way the value travels: down into the called module, or up as its result.

// id goes down, the check registered under it comes back up
Flag

A value whose job is to steer what a module does next. The filled circle marks the tail. Every flag in Probe.java is a thrown exception, which sends the caller to its catch block.

throw new Runaway(String.format("Still running after %d steps", MAX_EVENTS));   // in add
Conditional call

The diamond means the call happens only when a test passes.

A method from the JDK that Probe.java calls but does not define.

Module in another file

Couples take the name of the variable in the code, letting you find each one in Probe.java. Where the code passes a value straight on without storing it in a variable, the couple takes a short name for it, such as Enter for the record that enter passes to add, or answer for the boolean that Check.eval returns.

A flag is drawn once, on the call where its exception starts. Probe.java catches none of them, and each one carries on up through every caller to the code that called the entry point.

Each recording method builds an event record, such as new Enter(method). Java writes the constructors of those records, which are left out of the charts and the count. Calls to List and String methods are left out too, apart from List.copyOf, which is the whole job of getEvents. The Error constructor that new Runaway passes its message to is left out as well. The private constructor Probe() stops other code making a Probe object. Nothing calls it, and it is left out of the 18 modules.

Fan-in and fan-out

Fan-in is the number of modules that call a module. Fan-out is the number of modules it calls. Yourdon and Constantine want high fan-in for small shared helpers, since it means one piece of code serves many callers, and moderate fan-out, since a module that calls too many others is hard to follow. add has a fan-in of 6, the highest in the file, because every method that records an event goes through it. check(int, int, int) calls four modules, the most in the file and well within the usual rule of thumb of about seven.

Thirteen modules have a fan-in of 0, since Trace.fillCheck is the one caller of Probe in src/main.

What the charts say about the design

Structured Design judges a design by two measures. Coupling is how much one module depends on another, and the couples on a chart are its visible part: fewer and simpler couples mean looser coupling. Cohesion is how closely the statements inside one module serve a single job. A chart shows coupling directly, and these notes read the charts that way.

add guards every event

Six modules record an event, and all six do it through add. The check against MAX_EVENTS therefore lives in one place, and a new kind of event gets the limit by calling add. Yourdon and Constantine call this factoring: a job shared by several modules moves into one module beneath them, raising its fan-in.

Every module shares the static lists

EVENTS, CHECKS and loops are static fields, and most modules read or change them without any couple on a chart. Yourdon and Constantine call this common coupling, and rank it among the tightest kinds, since any module can change what another one sees. The reporting copy calls Probe through static methods, meaning it holds no Probe object to pass along, and the static fields are the place the events can go. The class Javadoc states the cost: Probe records one traced call at a time, on one thread.

Two callers turn a yes-or-no into a number

checkSame passes 0 when both objects are the same and 1 when they differ, and checkNull passes 0 for null and 1 for an object. Each also passes 0 as the right-hand value. The registered check then decides the answer: for node != null, an object becomes 1 != 0, which is true. As a result, one module records every kind of check, at the price of a number that stands in for a boolean.

Runaway passes through the student’s code

A Runaway starts in add or loop and travels up through every traced method on the way to the code that started the call. Runaway extends Error, meaning a catch (Exception e) in the student’s method lets it pass. The flag is aimed at the code that ran the call, and the modules in between have no say in it.
