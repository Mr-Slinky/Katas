Couples take the name of the variable in the code, so you can find each one in SourceCode.java. Where the code passes a value straight on without storing it in a variable, the couple takes a short name for it, such as source for the SourceCode that find(Class) returns, or bytes for the array that Files.readAllBytes returns.

preVisitDirectory, visitFile and visitFileFailed are methods of the anonymous SimpleFileVisitor that find(Class, Path) builds. Files.walkFileTree is the module that calls them, so they sit beneath it. Calls to String, Path, List, Set, Optional and Comparator methods are left out, along with Class.getName.

Fan-in and fan-out

Fan-in is the number of modules that call a module. Fan-out is the number of modules it calls. Yourdon and Constantine want high fan-in for small shared helpers, since it means one piece of code serves many callers, and moderate fan-out, since a module that calls too many others is hard to follow. find(Class, Path) calls four modules, the most in the file and well within the usual rule of thumb of about seven. No module has a fan-in above 1, because SourceCode.java has no helper that two modules share.

Five modules have a fan-in of 0, since nothing in src/main calls SourceCode yet. Three of them, hasLines, getLineCount and getFileName, call nothing either, so they appear in this table and on no chart.

What the charts say about the design

Structured Design judges a design by two measures. Coupling is how much one module depends on another, and the couples on a chart are its visible part: fewer and simpler couples mean looser coupling. Cohesion is how closely the statements inside one module serve a single job. A chart shows coupling directly, so these notes read the charts that way, with one note on cohesion at the end.

The visitor tells the library what to do

preVisitDirectory returns SKIP_SUBTREE or CONTINUE, and Files.walkFileTree obeys it. That is a flag travelling upward to steer the caller, which Meilir Page-Jones, writing on Structured Design, calls an inversion of authority: the module below gives the orders. In a callback API such as FileVisitor that reversal is the whole point, since the library hands each decision to the code that knows the answer. visitFile and visitFileFailed always return CONTINUE, so their flags never change what the walk does.

The visitor shares three variables without couples

The visitor reads root and wanted from find(Class, Path), and adds each match to matches. Java lets an anonymous class use a local variable of the method around it when that variable is never reassigned, and matches qualifies because the code changes the list’s contents rather than the variable. None of this sharing appears on Chart 1, which is the risk Yourdon and Constantine see in data that bypasses the couples. Here the visitor lives only inside find(Class, Path) and only for one walk, so the hidden sharing stays within a single method.

find turns a failure into data

Files.walkFileTree and readLines can each throw an IOException, which reaches find(Class, Path) as a flag. find(Class, Path) catches it and returns a SourceCode with no lines, so the flag stops there. A caller asks hasLines instead of writing a catch block. readLines treats a CharacterCodingException the same way, answering it with a second read as Windows-1252 rather than passing it on.

find(Class, Path) does four jobs in a row

It works out the wanted path from the class name, walks the folders, picks the nearest match, then reads it. Each job feeds its result to the next, which Yourdon and Constantine call sequential cohesion, the level just below a module that does one job. The first job, lines 101 to 106, takes a Class and produces a path, so it could become a module of its own with one couple in and one out. fileName is the last part of wanted, meaning that module could return wanted alone, with wanted.getFileName() giving the name back.
