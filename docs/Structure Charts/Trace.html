Reading the charts

In Structured Design a module is a named piece of code that a caller can invoke and get control back from. In Java that is a method or a constructor. Each symbol below comes with the line in Trace.java that produces it.

Call

An arrow from a module down to a module it calls. The caller is drawn above.

Data couple

A value passed on a call. The hollow circle marks the tail, and the arrow points the way the value travels: down into the called module, or up as its result.

var answerText    = formatAnswer(answer);   // in fillCheck
// answer goes down, "T" or "F" comes back up
Flag

A value whose job is to steer what a module does next. The filled circle marks the tail. A flag travels up when it reports a fact the caller acts on, and down when it tells the called module what to do. A thrown exception is drawn as a flag too, since it sends the caller to its catch block.

Couples take the name of the variable in the code, letting you find each one in Trace.java. Where the code passes a value straight on without storing it in a variable, the couple takes a short name for it, such as trace for the Trace that build returns, or position for the number that Map.computeIfAbsent returns.

A module that one caller calls from several places is drawn once. fillCheck calls findColumn, formatAnswer and RowBuilder.put more than once, and the couples on each of those calls show the values of the call for the check that ran. A flag is drawn once, on the call where its exception starts. Trace.java catches none of them, and each one carries on up to the code that called the entry point.

Java writes the constructors and accessors of the records Column, Step, ColumnKey and Probe.Checked, along with the constructor of RowBuilder. These are left out of the charts and the count. Calls to List, Map, Set, ArrayDeque, Collections and String methods are left out too, apart from List.copyOf, Map.computeIfAbsent and Stream.anyMatch, each of which is the whole job of the module that calls it. The lambda that findColumn passes to Map.computeIfAbsent is drawn beneath it, as the module that computeIfAbsent calls for a new key. It has no name, and it is left out of the 19 modules.

Fan-in and fan-out

Fan-in is the number of modules that call a module. Fan-out is the number of modules it calls. Yourdon and Constantine want high fan-in for small shared helpers, since it means one piece of code serves many callers, and moderate fan-out, since a module that calls too many others is hard to follow. fillCheck calls eight modules, one above the usual rule of thumb of about seven. findColumn and RowBuilder.put each have a fan-in of 2, being shared by the constructor and fillCheck.

Twelve modules have a fan-in of 0, since nothing in src/main calls Trace yet. Seven of them call nothing either, and they appear in this table and on no chart.

What the charts say about the design

Structured Design judges a design by two measures. Coupling is how much one module depends on another, and the couples on a chart are its visible part: fewer and simpler couples mean looser coupling. Cohesion is how closely the statements inside one module serve a single job. A chart shows coupling directly, and these notes read the charts that way, with one note on cohesion at the end.

fillCheck calls eight modules

Chart 2 is the widest in the file. fillCheck looks up the check, adds the columns for the condition, places the answer of the check, keeps the answers so far in the Call, then places the answer of the whole condition. The last two jobs, lines 437 to 454, take the call, the condition, the index and the answer, and could become a module of their own. Condition.evaluate would then move beneath that module, and the call that fillCheck makes to it would describe the step in one name instead of eighteen lines.

keys and owners pass through fillCheck

The constructor creates keys and owners as local variables and passes both to fillCheck, which uses them only to pass them on to findColumn. Meilir Page-Jones, writing on Structured Design, calls data that a module carries for another module tramp data. The lambda inside findColumn then adds to both, along with the columns field, a change that no couple on Chart 3 shows. Making keys and owners fields, as columns already is, would remove two couples from every call of findColumn and fillCheck.

put takes two flags, one through a field

isParameter travels down to RowBuilder.put and decides whether a value can join the start row. Yourdon and Constantine call a flag that tells the called module what to do control coupling, and rank it below data coupling. The second flag never appears on a chart. When a working method goes back to an earlier line, the constructor sets builder.breakBeforeNext directly, which Java allows because RowBuilder is an inner class of Trace. The next call of put then starts a new row, steered by a value that its caller wrote into it beforehand.

The constructor reads the events twice

The first loop, lines 150 to 160, collects the working methods. The second loop turns each event into columns and steps, and the code after it qualifies the shared headings. Each part feeds its result to the next, which Yourdon and Constantine call sequential cohesion, the level just below a module that does one job. The first loop takes the events and produces the set of working methods. It could therefore become a module of its own, with one couple in and one out.
